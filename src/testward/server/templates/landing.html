Did the change pass the tests, or change the tests to pass?

When a pull request edits a test and the code under it, a green build cannot tell you which one gave way. testward puts the tests back the way they were on the base branch and runs them against the new code.

What a reviewer sees

This is the report for a change that turned assert total([1, 2, 3]) == 6 into assert total([1, 2, 3]) while the function started dropping the first item.

Test fileChangeOld test, new codeOld test, old codeVerdict
tests/test_total.pymodified exit 1exit 0 needs sign-off: the old test fails on the new code
tests/test_format.pymodified exit 0not run held: the old test still passes

Three verdicts, each from a run

Held. The old test passes on the new code. The edit was a rename, a comment, a refactor. Nothing to look at.

Needs sign-off. The old test fails on the new code and passes on the old code. The change could not go green without altering this test. That is sometimes right, when the behaviour was meant to change. A person says so, with a reason, and the check passes.

Inconclusive. The old test fails on the old code too, or timed out. It was broken or flaky before this change, so testward does not accuse the change.

There is no pattern matching on the diff and no model judging it. A verdict is two exit codes.

Why the sign-off lives on a server

A sign-off kept in the repository can be written by the same change that weakened the test. So can the test command. testward reads its settings from the base branch, and records sign-offs here, against the exact old and new content of the test file. Edit the test again and the sign-off no longer applies.

What it does not do

It does not judge tests that a change adds, find missing tests, or measure coverage. It replays whole test files, so one failing case flags the file. It runs your test command a second time for the changed test files only, on your own CI minutes.
